# 복원 — 무엇이 돌아오고, 그것을 어떻게 판정하는가

프로세스가 끝날 때 열려 있던 창은 다시 시작할 때 같은 레이아웃으로 돌아옵니다. **판정은 숫자
하나입니다**: 재시작 전후의 `sok state.fingerprint`, 그리고 둘은 같습니다.

## 범위

무엇을 저장하고, 무엇이 돌아오고, 무엇을 의도적으로 넘기지 않는지 기술합니다. 저장소 자체는
`core/store` 이며, 이 문서는 거기에 기록되는 형태와 그것을 읽는 부팅입니다.

# P. 저장

## P1. 키 둘, 각각의 용도

| 키 | 담는 것 |
| --- | --- |
| `windows` | 원장 — 돌아와야 할 창마다 슬롯 하나, 그 root 들과 프레임 |
| `window/<label>` | 창 하나의 레이아웃: workspace, space, 분할 트리, 활성 pane, rail 배치 |

원장은 **무엇이 돌아오는가**의 기록입니다. 스냅샷은 **어떤 모양이었는가**의 기록입니다. 둘은 서로
다른 질문에 대한 기록이고 창에는 둘 다 필요합니다.

## P2. 원장은 종료가 아니라 창을 닫을 때 기록한다

창을 닫으면 그 슬롯을 제거합니다. 그렇게 하지 않으면 다음 부팅이 사람이 닫은 창을 되살립니다. 종료는
제거하지 않습니다. 종료는 모든 창을 닫으므로, 그때 원장을 비우면 다음 실행에서 아무 창도 열리지
않습니다.

따라서 한 번도 닫히지 않은 창이 열려 있는 동안 원장에 없는 것은 정상입니다.

## P2-1. 내구 쓰기는 발행하지, 파일 안으로 쓰지 않는다

읽는 쪽이 읽는 그 파일 안으로 쓰는 것은 한 단계가 아닙니다. open 이 truncate 하므로, truncate 와
마지막 바이트 사이에 도착한 리더는 옛 내용도 새 내용도 아닌 파일을 봅니다. 도중에 끊긴 쓰기는 그것을
디스크에 영구히 남깁니다.

2026-09-03 측정: 평범한 쓰기에 대한 동시성 프로브에서 리더가 첫 라운드에 1 MiB 값의 **0 바이트**를
읽었습니다. 다섯 곳이 그 모양이었습니다 — 플러그인이 저장한 값, 크래시 후 복구가 읽는 install commit
journal, 사이드카의 adoption 기록, 사람의 파일 저장, 그리고 이 저장소의 작업 흐름이 찍자마자 읽는 창
캡처.

`core/atomicfile.Publish` 가 그 하나의 방법입니다. 내용을 같은 디렉터리의 이웃에 쓰고 그 이웃을 대상
위로 rename 하며, 그것은 한 단계입니다. 남은 모든 `os.WriteFile` 은 "리더가 쓰기 도중에 도착할 수 없는
이유" 와 함께 하나씩 열거되어야 통과합니다.

쓰기마다 자기 이웃을 씁니다. 프로세스당 하나의 이름을 공유하면 동시 쓰기 둘의 절반씩을 발행합니다 —
같은 스플라이스가 한 단계 뒤로 옮겨진 것입니다.

링크인 경로는 그것이 가리키는 대상 위로 발행합니다. rename 은 착지한 것을 대체하므로, 파일을 심링크로
놓아 둔 사람은 저장 후에도 링크가 살아남기를 기대합니다. 이 저장소는 자기 링크를 만들지 않습니다. 두
번째 검사가 그것을 지키고, 경로는 선언된 것에서 해석합니다.

플래터에 닿는 것은 한 단계인 것과 별개 문제입니다. 프로세스 종료를 넘어야 하는 쓰기는 운영체제가
가지면 끝이고, 전원 차단을 넘어야 하는 쓰기는 아닙니다. page cache 가 그것을 넘지 못하기 때문입니다.
두 번째 종류만 `Sync` 를 냅니다 — `SESSION.md` S4-5 를 보십시오. 정지 쓰기가 그것입니다.

## P3. 슬롯 없는 스냅샷은 제거한다

2026-08-16 실측: 원장에 슬롯 3개, 저장소에 스냅샷 24개. 창을 열고 닫은 모든 실행이 자기 기록을 영구히
남겼습니다. 그것은 무한 증가이며, 더 이상 존재하지 않는 빌드가 쓴 기록이 남아 걸림돌이 된 경위이기도
합니다(K1).

메인 부팅은 어떤 슬롯도 지목하지 않고 살아 있는 창도 보유하지 않은 `window/<label>` 을 전부
제거합니다. 살아 있음이 중요합니다. 원장만으로 쓸어내면 사람이 보고 있는 창의 기록을 지웁니다.
**창 census 가 없으면 아무것도 쓸어내지 않습니다** — 읽을 수 없는 census 는 열린 창을 모두 없는 것처럼
만듭니다.

실측: 이것이 들어간 다음 실행은 기록 21개를 제거하고 키 12개를 유지했습니다. 그다음 실행은 0개를
제거했습니다.

# R. 복원

## R0. `main` 은 부트스트랩 창이지 유지되는 workspace 가 아니다

Wails v3.0.0-beta.12 는 최상위 창마다 별도 `WKWebView` 를 만들고, 각 창은 프론트엔드를 독립적으로
적재합니다. 따라서 workspace 복원 후에도 시작 시점의 `main` 창을 유지하면 WebContent 힙과 그래픽
backing store 를 하나 더 보유하게 됩니다.

시작 시점의 `main` 창은 저장된 모든 workspace 창을 복원하고 `control_plane_bootstrap_complete` 를
보고합니다. 다음 두 사실이 모두 참이 된 뒤에만 닫힙니다.

1. 저장된 모든 창을 요청했다;
2. workspace 렌더러 중 최소 하나가 자기 명령 카탈로그를 선언했다.

둘 다 이벤트입니다. 타이머도 폴링 루프도 없습니다. workspace 렌더러가 없으면 `main` 이 남아
애플리케이션에 쓸 수 있는 창이 유지됩니다. 명시적인 `window.open mode=orchestrator` 는 같은 예약
이름을 써서 `main` 을 다시 만들며, 일회성 부트스트랩 상태는 그것을 닫지 않습니다.

애플리케이션은 프로세스 재사용이나 캐시 축출을 강제하는 비공개 WebKit API 를 쓰지 않습니다.

## R1. 읽을 수 없는 기록은 그 기록만 잃는다

모든 스냅샷은 무엇이 잘못됐는지 이름 짓는 형태 검사를 지납니다. 유효하지 않은 기록은 보고하고
건너뛰며, 복원 루프를 끝내지도 그 기록을 다시 쓰지도 않습니다. 리더 하나가 현재 형태 하나를 받습니다.
빠진 상태를 채우지 않습니다.

## R2. 읽지 못함은 비어 있음이 아니다

읽을 수 없었던 스냅샷은 읽지 못함으로 보고합니다. workspace 0개로 기록하면 한 번도 쓰지 않은 창과
같아지고, 그러면 저장 가드가 열려 이 빌드가 파싱하지 못했을 뿐인 기록을 덮어씁니다.

## R3. 모든 식별자를 유지한다

2026-09-05 부터 스페이스는 `{groups, plane}` — pane 들과 라이브러리 평면 상태, rail 의 slot 포함 —
로 저장되고, `layout` 아래 split tree 를 든 레코드는 이름을 대고 거부한다 (PANE-PLANE S). 다른
모양의 rail placement 는 그 필드만 잃는다.

식별자는 유일하도록 발급하며, 상태를 그것에 매달 수 있도록 유지합니다. 터미널 세션의 키는
`windowLabel + "|" + paneId` (`soksak-plugin-terminal-xterm`, `command/session.go` — `paneKey`)
입니다. 새 id 로 돌아온 pane 은 쓰던 shell 에 다시 붙을 수 없습니다. 세션은 여전히 실행 중이고
스크롤백과 작업 디렉터리를 그대로 보유하는데, 더 이상 아무것도 그것을 주소로 지목하지 못합니다.

pane·view·workspace 를 키로 삼는 다른 모든 것도 같습니다 — 플러그인 상태, 사람이나 에이전트가 적어 둔
주소, projection seed. id 를 유지하는 것이 그것들을 지속 가능하게 만듭니다.

**예외 없음.** 분할 노드는 이 빌드가 다시 발급하던 하나였습니다. 아무것도 참조하지 않는다는
이유였는데, 2026-08-16 실측으로 스냅샷에도 `state.tree` 에도 `ui.tree` 에도 없었습니다. 그 결과 복원이
이름을 바꾸는 id 종류가 하나 생겼고, 리더는 그 이름이 그대로 남는지 판단하기 전에 자기가 어떤 종류를
들고 있는지 먼저 확인해야 했습니다.

모든 기록에 그 필드가 있어야 합니다. 거부는 무엇이 빠졌는지 이름 짓고, 기록을 그대로 두며, 그 기록만
잃습니다(R1). 역직렬화기는 지속 식별자를 생성하지 않습니다.

유일성과 지속성은 여기서 상충하지 않습니다. 상충한 것은 id 가 카운터였던 동안뿐입니다 — `t1` 이 서로
다른 창 스냅샷 셋의 workspace id 였던 이유는 카운터가 같은 값에서 다시 시작하기 때문이지 id 를
유지했기 때문이 아닙니다. 발급자가 만든 식별자(N1: `crypto.getRandomValues` 에서 나온 base32 여섯
자)는 유지하는 한 유일합니다.

2026-08-16 실측이며, 적어 두는 이유는 이것입니다. 복원 시 모든 id 를 새로 발급한 변경이 digest 검사를
통과하면서 재부착 키를 깨뜨렸습니다. `state.fingerprint` 는 id 를 담지 않습니다 — 그것이 판정하는
대상인 레이아웃의 형태에는 맞습니다 — 그래서 digest 는 이것을 볼 수 없고 판정 전부가 아닙니다.

검사: `frontend/src/state/restoreKeepsIds.test.ts`.

# V. 판정

## V1. `sok state.fingerprint` — 숫자 둘, 섞지 않는다

```
digest                 형태: 아래 전부, 그리고 식별자 없음
ids                    창이 보유한 모든 식별자, 정렬됨
workspaces[].root      workspace 의 identity (P4), id 가 아님
             mode      flow | pin
             station   유효한 rail 라인
             cleanLines[]
             spaces[].panes[].{ rect, active }
```

**GREEN: 재시작 전 두 숫자가 재시작 후 두 숫자와 같습니다.** 어느 쪽이 움직였는지 불일치가 이름 지을
수 있도록, 부분들을 `digest` 옆에 함께 반환합니다.

질문이 둘이므로 숫자도 둘입니다. `digest` 는 사람이 보는 것입니다. 이름을 바꿔도 거기서는 아무것도
움직이지 않으며 그것이 맞습니다. 같은 사각형들을 다른 이름을 가진 두 창은 같아 보이기 때문입니다.
`ids` 는 그것들이 무엇인지입니다. 터미널 세션은 `windowLabel + "|" + paneId` 를 키로 하므로, 새 이름을 받아
돌아온 pane 은 모든 사각형이 그대로 있어도 자기 shell 을 잃습니다.

둘은 나란히 답이 나오며 결코 합치지 않습니다. 둘을 하나로 덮는 숫자는 이름 변경에도 크기 변경에도
똑같이 움직이고, "무언가 움직였다" 만 통보받은 호출자는 어느 쪽인지 따로 찾아야 합니다 — 그 읽기는
어떤 결함도 이름 짓지 못합니다.

사각형은 소수점 아홉째 자리로 반올림합니다. 같은 해를 두 번 계산해도 double 의 마지막 비트가 다르고,
그것까지 포함하는 digest 는 두 번 일치하지 않습니다. workspace 는 root 순으로 정렬하므로, 같은
workspace 를 다른 순서로 복원해도 차이로 보고하지 않습니다.

검사: `restore_gate_test.go`, `go tool wails3 task verify:application` 이 실행합니다. 바이너리 둘을
빌드하고, 전용 home 으로 애플리케이션을 시작하고, workspace 창을 열고, digest 를 읽고,
`app.shutdown.commit` 으로 종료하고, 다시 시작해 두 번째로 읽습니다.

이 검사는 명령의 응답을 비교하며 자기 판정을 조립하지 않습니다. 트리를 걸어 이름을 스스로 판정하는
검사는 같은 재시작에 대한 두 번째 규칙이고, 둘 중 하나를 고치는 날 서로 어긋납니다 — `digest` 가
존재하는 이유입니다(V1 도입부).

프로세스를 강제 종료하는 대신 명령으로 종료하는 것이 이 검사가 존재할 수 있는 이유 전부입니다.
강제 종료는 drain 과 save 를 건너뛰므로, 그때 돌아오는 것은 크래시의 측정입니다.

## V2. 콜드 재시작 한 번은 측정이 아니다

검사는 pane 3개 레이아웃에 브라우저 탭과 고정된 rail 을 두고 콜드 재시작 6회를 실행합니다. 모든
digest 가 일치해야 하고, 원장은 슬롯 3개를 유지해야 하며, 마지막 sweep 은 0개를 제거해야 합니다.

  아니라 레이아웃의 결과입니다.
