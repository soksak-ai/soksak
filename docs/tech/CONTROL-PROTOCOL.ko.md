# Control protocol

애플리케이션 밖의 무언가가 애플리케이션에 연결하는 방법입니다. `cmd/sok` 은 그런 클라이언트 중
하나이며, 프로토콜에는 그것에 특화된 것이 없습니다.

## C1. 한 줄 JSON, 양방향

요청은 한 줄에 담긴 JSON 객체 하나입니다. 전송은 framing 이 없는 바이트 스트림이며, 길이 접두사를
붙이면 소켓을 손으로 읽을 수 없게 됩니다. 그것이 사람이 조작할 수 있는 control plane 과 클라이언트를
작성해야만 쓸 수 있는 control plane 의 차이입니다.

```
{"id":"1","command":"state.commands","args":{}}
{"id":"1","ok":true,"result":{...}}
```

## C2. Envelope

요청: `id`, `command`, `args`.

- `id` 는 그대로 되돌려주며 해석하지 않습니다. 클라이언트가 파이프라이닝하고 자기 기준으로 대조할 수
  있습니다.
- `command` 는 registry 항목을 지목합니다. registry 밖에는 아무것도 없습니다.
- `args` 는 명령이 디코드할 때까지 인코드된 채 있으므로, 이 구분은 그 모양을 받지 않습니다.

응답: `id`, `ok`, `result`, `error`.

`ok` 는 빈 `error` 로 추론하지 않고 명시합니다. 그렇지 않으면 결과가 null 인 명령과 빈 메시지로 실패한
명령이 같은 세 바이트가 됩니다.

## C2a. 이 plane 의 응답 형태는 하나

`result` 는 항상 `{code, data}` 입니다. 창의 명령은 자기 envelope — `ok`, `code`, `data`, `message`,
`hint` — 로 답하고 중계가 그것을 통째로 전달합니다. 이 프로세스가 서비스하는 명령에는 값을 들여다보는
대신 누가 서비스하는지에 대한 registry 자신의 기록에서 같은 형태를 소켓 지점에서 적용합니다.

프로세스 안의 호출자는 다른 청중이며 값을 그대로 유지합니다. `invoke` 를 부르는 창은 명령 이름을 알고
호출 지점에서 타입을 갖습니다. 이 형태는 호출자가 일반적인 plane 을 위한 것입니다.

## C3. greeting 이 버전을 협상한다

`system.hello` 는 예약어입니다. 그것을 등록한 기능 패키지는 협상을 다르게 답하는 무언가로 바꿔버립니다.
이 명령은 이 빌드가 말하는 프로토콜 버전, 설치본 identity, 전체 명령 표를 반환합니다.

버전 불일치는 다르게 동작하는 첫 명령이 아니라 greeting 에서 거부합니다. 중간에 발견된 불일치는 이미
호출자가 신뢰한 답을 만들어 낸 뒤입니다.

identity 를 greeting 에 두는 이유는, 잘못된 소켓에 연결한 클라이언트가 나중에 놀라운 답을 받는 대신
즉시 알게 하기 위함입니다.

명령 표를 greeting 에 두는 이유도 같습니다. 따로 조회해야 하는 클라이언트는 확인하지 않은 이름을 써서
행동하게 됩니다.

## C4. 명령 표가 스스로 설명한다

`Table` 은 이 빌드가 서비스하는 것과 거부하는 것을 담고, 모든 거부는 그것을 막는 이유를 담습니다.
"알 수 없는 명령" 과 "여기서는 빌드되지 않음" 은 호출자를 서로 다른 곳으로 보내며, 탐색을 끝내는 것은
후자뿐입니다.

**검사.** `frameworks/wails/coverage_test.go` 가 registry 에서 표를 읽어, 프론트엔드가 서비스되지도
거부되지도 않는 이름을 호출할 때, 거부에 호출자가 없을 때, 거부에 이유가 없을 때 실패합니다.

네이티브 창 생성 receipt 는 그 렌더러가 명령을 등록했다는 뜻이 아닙니다. `window_renderer_wait` 가
정확히 한 창에 대한 선언 이벤트를 유한한 기한으로 기다립니다. 성공한 뒤에는 `app.boot.wait` 같은
렌더러 명령을 명령 표를 폴링하지 않고 주소로 부를 수 있습니다.

`timeoutMs` 를 선언한 위임 렌더러 명령의 경우, 중계 기한은 명령 기한보다 최소 5초 깁니다. 중계가 도메인
timeout 을 같은 순간의 전송 timeout 으로 대체해서는 안 됩니다. timeout 을 선언하지 않은 명령은 고정된
중계 기한을 유지합니다.

## C5. 주소, 그리고 누가 연결할 수 있는가

소켓 경로는 identity 에서 한 번 도출하며(`<home>/<identifier>.sock`, IDENTITY.ko.md I4) 두 번째로
적지 않습니다.

모드는 0600 입니다. 소켓은 이 빌드가 가진 모든 명령에 답하므로 연결할 수 있는 쪽은 애플리케이션이 할
수 있는 모든 것을 할 수 있습니다. 그룹 읽기가 가능한 소켓은 그 권한을 사용자가 실행하는 모든 프로세스에
넘기는 것입니다.

종료된 프로세스가 남긴 소켓 파일은 bind 전에 제거합니다. 대신 거부하면 크래시마다 수동 정리가 필요해지고,
파일은 잠금이 아닙니다 — 살아 있는 소유자는 여전히 주소를 보유하므로 bind 가 실패하며 그 사실을
알립니다.

경로 한계는 darwin 과 linux 중 낮은 쪽인 104 바이트입니다. 그래서 여기서 동작하는 home 은 이 빌드가
도는 모든 곳에서 동작합니다. 넘기면 "invalid argument" 로 실패하는데, 그 메시지는 경로에 대해 아무것도
보고하지 않습니다.

## C6. Windows

Windows 는 같은 envelope 를 나르는 named pipe 를 씁니다. identity 가 런타임 루트와 설치본 식별자에서
불투명한 pipe 이름 하나를 도출하며, 애플리케이션 listener, `sok`, 사이드카 호스트가 그 주소를 파일
경로로 변환하지 않고 사용합니다. pipe ACL 은 현재 프로세스 사용자에게만 접근을 허용합니다.

Windows 시스템 검증은 아직 완료되지 않았습니다. PTY 사이드카에 named-pipe listener 가 필요하고,
애플리케이션·`sok`·사이드카 호스트·ConPTY 프로세스가 Windows 에서 설치된 터미널 시스템 스위트를
통과해야 합니다. 크로스 빌드는 그 런타임 판정이 아닙니다.
