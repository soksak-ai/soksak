# 네이티브 계층

플랫폼을 직접 다루는 코드의 규칙과, 나머지 애플리케이션을 그것에서 떨어뜨려 두는 구분의 규칙입니다.

## cgo 가 여기 있는 이유

프레임워크는 macOS 와 Linux 에서 cgo 로 컴파일됩니다. 자기 창과 webview 가 그렇게 작성되어 있습니다.
그 플랫폼의 빌드는 우리가 cgo 한 줄을 추가하든 않든 cgo 빌드이므로, 거기서 "cgo 없음" 은 선택할 수
있는 목표가 아닙니다.

Windows 는 다릅니다. 프레임워크가 순수 Go 의 COM 으로 WebView2 에 도달하므로, 그 target 은 어떤
호스트에서도 툴체인 없이 크로스 컴파일됩니다.

관심사의 전체 모양이 그것입니다. cgo 를 피할 이유는 크로스 컴파일이고, 피하는 것이 무언가를 바꾸는
곳은 Windows 뿐입니다.

## N1. cgo 표면은 작고 고정되어 있다

순수 Go 로 가능한 모든 것은 순수 Go 입니다. 인벤토리 검증, 순서 결정, 배치 계획, receipt 에는 플랫폼
호출이 없습니다. cgo 는 계층 하나를 담습니다 — "이 배치를 메인 스레드에서 적용하고 그 결과 프레임을
보고하라."

`"C"` 를 import 하는 파일 집합은 고정되어 있습니다. 새 파일에는 명시된 이유가 필요합니다.

## N2. 네이티브 소스는 자기 파일에 정의한다

Objective-C, C, C++ 는 `.m`, `.h`, `.c` 파일에 둡니다. cgo 서문에는 `#cgo` 지시자와 우리 헤더의
`#include` 만 둡니다.

주석 안에는 구문 강조도, 별도 컴파일 단위도, 네이티브 코드를 그 자체로 테스트할 방법도 없습니다.
프레임워크 자신이 이렇게 작성되어 있습니다.

## N3. Windows 는 cgo 없이 유지한다

검사: `CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build ./...` 가 `task verify` 에서 실행됩니다.
Windows 경로로 cgo 를 끌어들이는 것은 즉시 RED 가 됩니다. 이것이 크로스 컴파일 관심사를 선호가 아니라
측정된 사실로 유지합니다.

## N4. document view 크기 조정은 플랫폼 소유자에게 둔다

Windows 와 Linux 에서는 Wails 가 document view 크기 조정을 소유합니다. Windows 는 `WM_SIZE` 에서
WebView2 컨트롤러를 갱신하고, Linux 는 GTK allocation 으로 webview 를 갱신합니다. 코어는 두 플랫폼에
두 번째 크기 계약을 추가하지 않습니다.

macOS 에는 측정된 프레임워크 계층 결함이 하나 있습니다. document view 가 보이는 콘텐츠 영역보다 1
포인트 커질 수 있습니다. 코어는 각 창이 네이티브 수명을 얻은 뒤 Darwin 구현에서만 그 계층을 고칩니다.
그 수리는 `WindowHost` 의 일부가 아니며 다른 플랫폼의 부팅을 막을 수 없습니다.

## purego 는 쓰지 않는다

검토했고 세 가지 이유로 기각했습니다. 그 이유가 유효한 동안만 기각도 유효합니다.

1. 창은 프레임워크가 만듭니다. 별도 FFI 경로로 거기에 닿는 것은 하나의 Objective-C 런타임을 두 방식으로
   다루는 것이며, 같은 규칙을 두 번 구현하는 일입니다.
2. cgo 는 컴파일러가 C 시그니처를 검사합니다. purego 는 아무것도 검사하지 않으므로 시그니처 오타가
   런타임 크래시가 됩니다.
3. 이 애플리케이션에 필요한 block 과 delegate 를 구조체와 런타임 클래스 등록으로 손수 만들어야 합니다.

N2 로 갚아나갈 수 있는 알려진 비용이 알 수 없는 비용보다 낫습니다.

## 캡처

창 캡처는 플랫폼 컴포지터 경로를 씁니다. 모든 백엔드가 다음 성질을 유지해야 합니다.

- 화면 녹화 권한이 필요 없습니다. 우리 창만 보기 때문입니다.
- 포커스가 필요 없고, 가려진 창도 캡처됩니다.
- 컴포지터의 결과를 캡처하므로 메인 webview 와 모든 네이티브 자식이 구멍 없이 한 이미지로 들어옵니다.
  webview 별 스냅샷으로는 그렇게 할 수 없습니다.

macOS 는 ScreenCaptureKit 으로 이 프로세스 자신의 공유 가능 콘텐츠를 읽습니다.
WebKit 이 완전히 가려져 프레임을 만들지 않았다면 캡처는 창을 key/main 으로 만들지 않고 앞으로
배치하고, 보이는 renderer가 실제 프레임 하나를 확인한 뒤 캡처하여 다시 뒤로 돌려놓습니다. 애플리케이션
활성화, 비공개 WebKit scheduling SPI, 폴링은 사용하지 않습니다.
`CGWindowListCreateImage` 는 macOS 15 에서 폐기되었고 렌더링 중 블로킹하므로 쓰지 않습니다. Linux 는
GTK 메인 스레드에서 GTK4 render node 를 스냅샷하고 그 텍스처를 인코딩합니다. X11 루트 창을 읽지
않으므로 가려진 창도 포커스 변경 없이 캡처됩니다. Windows 는 [CAPTURE.md](CAPTURE.md) 에 정의된 HWND
백엔드를 씁니다. 공유 픽셀 파이프라인과 그 로컬 크로스 빌드 검사가 거기에 문서화되어 있습니다.

출력 크기는 필터 스냅샷 **하나**에서 나옵니다: `contentRect` × `pointPixelScale`. 먼저 읽은 창 프레임을
나중에 캡처한 픽셀과 섞으면 나중 순간을 이전 크기로 리샘플하게 되고, 실시간 resize 중에는 화면에 있은
적 없는 프레임이 만들어집니다.

백엔드가 없는 플랫폼은 이름과 함께 실패합니다. 빈 바이트를 반환하면 "이 플랫폼은 캡처할 수 없다" 와
"창이 비어 있었다" 가 같은 답이 되고, 하류의 어떤 것도 둘을 구분할 수 없습니다.

## 네이티브 표면

애플리케이션은 표면을 DOM 에 선언하고 직접 배치하지 않습니다. 한 번의 전달에 완전한 인벤토리가
들어갑니다. 낡은 sequence, 부분 인벤토리, 두 번째 writer 는 무언가 바뀌기 전에 거부합니다. 그리고
receipt 하나가 실제로 적용된 것을 보고합니다.

좌표 계약은 좌상단 원점의 CSS 포인트이며 선언과 receipt 가 공유합니다. 그래서 합성 판정이 변환이 아니라
뺄셈이 됩니다.

선언 어휘에는 프레임워크 이름이 없습니다. 이 속성은 코어가 쓰므로, 거기에 프레임워크 이름이 있으면
코어가 다른 곳에서는 한 번도 부르지 않는 프레임워크 이름을 적게 됩니다.
