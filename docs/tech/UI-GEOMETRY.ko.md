# UI 기하 — 띠, 상자, 그리고 어느 선을 누가 그리는가

자유롭고 정확하게. 크기는 테마가 정하고, 1픽셀 어긋남은 구조적으로 불가능합니다. 주장은 그것
하나이며 기계가 지킵니다. 정적 검사 `frontend/src/ui/cssContract.test.ts`, 계약 표
`frontend/src/ui/borderContract.ts`, 그리고 실행 중인 창에 대한 `ui.validate` 와 `ui.expect`
입니다.

실패한 검사는 약화할 대상이 아닙니다. 표준 자체가 틀렸다면 그렇게 말하고 표준을 고칩니다.
말없이 우회하는 것은 이 문서가 명시적으로 금지하는 유일한 행동입니다.

## 범위

아래 각 규칙에는 그것을 만든 측정이 함께 있습니다. 규칙은 그 이유가 이 빌드에서 유효한 동안만
유효합니다. 바뀐 규칙 둘은 문서 끝에 무엇이 왜 바뀌었는지와 함께 기록되어 있습니다.

# A. 정렬

## R1. 띠의 padding 은 띠의 것

가로 띠 안의 세로 공간은 그 띠의 `padding-block` 변수만 소유합니다. 항목 — chip, 버튼, 컨트롤 —
은 남은 공간을 채우도록 늘어납니다.

- view 탭: `.view-tabs` 의 `--tab-pad` — 헤더 33 − 규칙선 1 = 안쪽 32, pad 4 → chip 24
- workspace 탭: `.tabs`·`.content-tabs` 의 `--ws-pad` — 37 − 1 = 안쪽 36, pad 5 → chip 26

따라서 항목 높이는 *도출값*입니다: 띠 안쪽 − padding × 2. 결과가 둘인데, 둘 다 의도한 것입니다.

- 같은 축의 형제 상자는 정의상 같은 높이입니다. 둘 사이의 1픽셀 차이를 표현할 방법이 없습니다.
- padding 이 정수이면 항목 위치도 정수입니다. 반픽셀 중앙 정렬이 생길 수 없습니다.

기각한 대안은 띠와 항목에 각자 높이를 주는 것이었습니다. 두 값의 홀짝이 어긋나면 항목이 반픽셀에
놓입니다 — 28짜리 chip 을 37 안에 중앙 정렬하면 y=48.5 에 놓이고 위아래 안티에일리어싱이 달라집니다.

테마는 padding 변수로만 크기를 정합니다. 항목 선택자의 `height:` 는 검사가 거부합니다(`auto` 는
예외). 예외는 가로 띠가 아닌 자리 — 정사각 workspace 레일과 세로 탭 목록 — 입니다.

**홀짝.** 띠의 안쪽 높이는 짝수입니다 — titlebar 45 − 1 = 44, chrome row 37 − 1 = 36, group header
33 − 1 = 32. 여기에 짝수 padding 을 쓰면 chip 도 짝수가 되고, chip 안의 짝수 내용(아이콘 12/14/16,
16짜리 닫기 상자)이 정수에 중앙 정렬됩니다. 반픽셀이 컴포넌트마다 쫓아다니지 않고 모든 층에서 한
번에 사라집니다.

## R1a. 이웃한 띠는 한 행

가로로 나란히 선 띠들은 하나의 행입니다. 왼쪽 헤더, 스페이스 탭, 오른쪽 헤더, 왼쪽 호스트 탭. 둘
사이에 1픽셀이라도 차이가 나면 그 사이의 선이 어긋납니다.

높이는 규칙 하나 — `--chrome-row-h` — 가 소유하며 개별 블록은 자기 높이를 선언하지 않습니다.

**사이드바와 콘텐츠 사이의 세로 방향에도 같은 규칙이 적용됩니다.** 사이드바 헤더와 콘텐츠 헤더가 한
행이고, 사이드바 푸터와 콘텐츠 푸터가 한 행입니다. 2026-08-15 이 빌드에서 실측: 콘텐츠 헤더가 33px,
사이드바 헤더가 30px 였고 두 행이 이음매 전체에서 3픽셀 어긋나 있었습니다. 테마마다 다른 색으로
그려져서, 어긋남이 테마마다 다른 결함처럼 보였습니다.

## R1b. pane inset 은 pane group 의 모든 레이어를 제한한다

사이드바, 콘텐츠 pane, 관계 장식은 동일한 내부 사각형을 사용합니다. host 사각형의 네 변을
`--pane-inset` 만큼 줄인 영역입니다. 그 내부 사각형이 pane 평면입니다 (PANE-PLANE P2): pane 의
rect 는 거기서 px 로 읽고, 두 pane 사이 복도는 inset 의 두 배 — 안쪽 변마다 절반씩, 테두리에는
없음 (split-pane R5) 입니다. 표면은 내부 좌표를 사용하는데 그 표면을 설명하는 장식만 host
외곽 좌표를 사용해서는 안 됩니다. 그렇게 하면 간격을 가로지르는 무관한 이음매가 생기고 사이드바의 우측
여백이 사라집니다. 따라서 노출된 관계 geometry 는 inset 원점에서 측정하고 inset 외곽선에서
끝납니다.

## R2. 정렬은 flex 가 소유한다

띠는 `display: flex; align-items: center` 입니다. absolute 배치, 음수 오프셋, margin 산술,
translate 보정으로 중앙처럼 *보이게* 만드는 것은 금지합니다. 그 보정은 폰트 하나, 확대율 하나,
테마 하나에만 맞습니다.

## R3. 규칙선은 구분선이지 margin 이 아니다

띠의 구분선은 `border` 로 그리며 레이아웃 공간을 차지합니다. 그러면 대칭은 "선 위 공간 = 선 아래
공간" 으로 판정되고, border 모델이 아무도 계산하지 않아도 그것을 만족합니다.

띠 높이는 `padding + 항목 + padding + 규칙선` 입니다. 모든 항이 정수입니다. `.content-tabs` 는
37 = 5 + 26 + 5 + 1.

## R3a. 테마는 변수이지 CSS 가 아니다

테마는 CSS 를 배포하지 않습니다. 임의 CSS 는 테마마다 R1 의 구조적 보장을 다시 깨뜨리고,
애플리케이션을 리팩터링할 때마다 모든 외부 테마가 조용히 깨집니다.

테마의 자유는 승인된 슬롯입니다. 색 토큰, 그리고 구조 손잡이 — `--tab-pad`, `--ws-pad`, 반경.
**손잡이가 없으면 슬롯을 추가하는 것이 옳은 행동**이며, 테마는 슬롯 밖을 건드리지 않습니다.

## R4. 좌표 산술은 CSS 규칙 하나가 소유한다

JSX 에서 `calc(...)` 문자열을 조립해 인라인으로 흩는 것은 금지합니다. 배치가 필요한 레이어는 변수
넷 — `--l`, `--t`, `--w`, `--h` — 을 받고, 산술은 App.css 규칙 하나에 정의합니다.

치수 상수(`--header-h`, `--status-h`, `--pane-inset`)는 TypeScript 소스 하나에서 한 번 주입합니다.

인라인 배치는 이유를 명시할 때만 정당합니다. 세션을 보존하는 지속 본문 슬롯, 구분선 *자체*인 split
divider, 오버레이인 drop indicator.

## R5. 정렬 주장은 숫자다

"보기에 맞다" 는 증거가 아닙니다. `sok ui.measure '{"address":"…"}'` 로 rect 를 얻어 형제의 y 와 h
가 일치하고 여백이 대칭인지 확인한 뒤에야 끝났다고 말합니다. 주소는 `sok ui.tree` 에서 얻으며 추측한
선택자를 쓰지 않습니다 — 노출되지 않은 요소는 측정할 수 없고, 그것이 요점입니다.

## R5b. 스크롤되는 노드는 내용이 상자에 맞지 않는 노드다

rect 는 화면이 노드에 준 상자이며 노드가 무엇을 담고 있는지는 보고하지 않습니다. `ui.measure` 는 그
옆에 `scroll` 을 반환합니다 — `top`, `left`, `width`, `height`, `clientWidth`, `clientHeight` —
그리고 `style` 에 `overflowX`, `overflowY`, `position` 을 반환합니다. client 상자보다 큰 내용은
맞지 않는다는 뜻이고, overflow 규칙과 함께 보면 잘렸는지, 스크롤되는지, 상위로 넘치는지가 갈립니다.

이 값들이 없을 때 pane 이 상자를 넘는 것을 볼 방법은 사람이 화면을 보는 것뿐이었습니다(2026-08-26
실측: 터미널 pane 이 받은 932 픽셀 중 384 만 그렸고, 보고는 스크린샷으로 왔습니다).

## R5a. 레이아웃 전체는 숫자 하나다

`ui.measure` 는 노드 하나를 읽습니다. 분할 레이아웃은 여럿이고, 하나씩 읽으면 뺄셈 — 그리고 그에
필요한 R4 산술 — 이 묻는 쪽에 남습니다.

`sok layout.verify` 가 활성 스페이스에 대해 그것을 합니다. pane 마다 선언된 rect(스페이스 상자의
백분율), 그 백분율이 R4 규칙에서 만들어야 할 rect, 측정된 viewport rect, 그리고 차이를 반환합니다.
**판정: `worst` 가 device pixel 하나 이내에서 0.** 배치가 이름을 대는데 화면이 그리지 않은 pane 은
`missing` 으로, 화면에 있는데 배치가 이름을 대지 않은 pane 은 `unexpected` 로 돌아옵니다. 둘 다 작은
차이가 아니므로 작은 차이로 보고하지 않습니다.

이 명령은 요소에서 되읽지 않고 백분율에서 위치를 다시 계산합니다. 렌더러와 산술을 공유하는 검증기는
렌더러의 실수까지 포함해 모든 것에 동의합니다.

**`settled` 를 먼저 읽으십시오.** 레이아웃 전환 중인 pane 은 목적지를 향해 보간되므로, 전환 중의
모든 숫자는 레이아웃이 아니라 한 프레임을 서술합니다. 응답에는 `settled` 와 열린 트랜잭션 id 가 함께
들어 있어 기억에 의존하지 않습니다 — 2026-08-16 실측, 빠른 분할 사이에 검증하면 차이가 100px 을
넘고 pane 32개가 missing 으로 세어졌는데, 전환이 닫힌 뒤에는 전부 0.013px 과 0 이었습니다.
`sok layout.transaction.wait` 로 기다린 뒤 다시 물으십시오.

들어가야 할 chrome 보다 작은 칸은 그리지 않고 거부합니다. `pane.split` 이 측정값과 하한과 함께
`TOO_SMALL` 을 반환합니다. 하한은 inset 쌍이며, 그 아래에서는 칸에 내부가 없어 CSS 가 너비를 0 으로
고정합니다 — 선언이 화면에서 더는 참이 아니게 되는 지점입니다. 분할은 행 전체를 재분배하므로 결과
칸을 모두 검사합니다. 공간이 모자라는 칸은 대개 아무도 이름을 대지 않은 칸입니다.

레일도 셈에 들어갑니다. 레일이 행에 삽입되므로 모든 칸이 백분율을 유지한 채 비례해서 픽셀을 잃습니다.
행은 스페이스 상자에서 레일 전체 너비를 뺀 값입니다. 2026-08-16 실측, 999px 스페이스에서 레일을 연
채 pane 하나는 827px 였습니다 — 999 에서 레일 160 과 inset 쌍 12 를 뺀 값입니다.

# B. 테두리 소유 — 어느 상자가 어느 변을 그리는가

1픽셀 어긋남이나 사라진 선의 근본 원인은 그 변을 아무도 소유하지 않는 것입니다. **모든 선에는 소유자가
정확히 하나 있습니다.**

RED 먼저, 그다음 GREEN: 검증기가 먼저 위반을 찾고, 그 뒤에야 무언가를 바꿉니다.

## B1. 외곽은 frame 의 것

패널의 바깥 네 변은 frame 오버레이가 배타적으로 소유합니다. 어떤 내부 요소도 바깥 변에 그리지
않습니다.

**소유는 표시가 아닙니다.** frame 이 무언가를 그리는지는 pane-style 토큰이 정합니다 — `flat` 은
아무것도 표시하지 않으며, 계약은 그 없음을 나타나서는 안 되는 상태로 검사합니다. 언급하지 않은 채 남기지
않습니다.

## B2. 본문은 아무것도 그리지 않는다

본문 — 터미널, 편집기, webview 슬롯 — 은 테두리를 소유하지 않습니다. 불투명한 내용이 자기 테두리를
덮으므로, 테두리는 존재하되 보이지 않게 됩니다.

본문 옆의 구분선는 본문을 마주 보는 쪽의 인접 chrome 띠가 소유합니다. 헤더는 아래, 푸터는 위, 왼쪽
chrome 은 오른쪽, 오른쪽 chrome 은 왼쪽입니다.

## B3. chrome 이 chrome 을 만날 때

두 chrome 표면이 만나면 본문에서 더 먼 쪽이 선을 소유합니다. titlebar 는 아래, 레일은 오른쪽입니다.

## B4. 토큰 둘, 색은 없다

구조선은 `var(--bd)` — 애플리케이션 chrome, 외곽, 부유 표면 — 이거나, 패널 안 규칙선이면
`var(--bd-soft)` 입니다. 후자는 `color-mix` 로 도출하므로 자기 테마 슬롯이 필요 없습니다. 강조는
`--accbg` 입니다.

border 선언에 리터럴 색을 쓰면 빌드가 실패합니다. 검사가 모든 border 선언을 이 기준으로 읽습니다.

## B5. frame 의 픽셀 예산

frame 은 오버레이이므로, 바깥 변에 닿는 요소는 그 변의 픽셀을 자기 예산에서 지불합니다. DOM chrome
띠는 `card` 와 `floating` 에서 padding 으로 지불합니다.

body slot 은 frame 의 왼쪽·오른쪽 lane 을 지불합니다(`--card-border-w`, `card`·`floating` 에서 1px,
`flat` 에서 0). slot 에 배치되는 것이 문서 위에 그려지는 네이티브 자식일 수 있기 때문입니다. pane 변까지
닿은 자식은 frame 을 덮었고, 자식 위에 frame 을 한 번 더 그리자 평면이 옮겨 간 뒤에도 그 frame 이 남았습니다
(NATIVE-SURFACES D1b.1). 검사: `frontend/src/ui/cssContract.test.ts` ("the body slot pays the frame's lanes").

## B6. 구분선 도구는 선을 소유하지 않는다

resizer 와 드래그 핸들은 폭 0 오버레이입니다. 선은 B2 나 B3 에서 그것을 소유한 쪽이 그립니다.

예외 하나: 불투명한 내용 둘 사이의 이음매 — 분할을 사이에 둔 터미널 둘 — 에는 테두리를 가질 DOM
소유자가 없습니다. 그 경우 `solid` divider 테마일 때, 구분선 도구가 위임으로 1픽셀 중앙선을
*표시*합니다. `overlay` 에서는 정지 상태에서 완전히 투명합니다.

## B7. 섞인 내용의 행은 컨테이너에서 중앙 정렬한다

텍스트와 아이콘이 섞인 행은 컨테이너에 `flex; align-items: center` 를 씁니다. 아이콘을 baseline
흐름에 넣지 않습니다. 세로 중앙 정렬은 상자가 아니라 — 테두리와 오버레이를 뺀 — 보이는 픽셀로
판정합니다.

## B8. 계약은 전면적이어야 한다

검증기는 등록된 표면만 봅니다. 검사 셋이 그것을 정직하게 유지합니다.

1. **CSS → 계약** — 구조 테두리를 그리는 선택자는 계약에 있거나, 위젯 외곽선(구분선이 아니라 닫힌
   도형)으로 명시 분류되어야 합니다. 알 수 없는 구분선는 실패입니다.
2. **계약 → CSS** — 계약의 규칙에는 그것에 답하는 선언이 있어야 합니다. 아무것도 가리키지 않는
   규칙은 규칙이 아닙니다.
3. **모든 상태** — 조건부 표면은 `paneStyle × divider` 공간 전체를 빠짐없이 모순 없이 덮어야 하며,
   존재해야 하는 상태와 **존재해서는 안 되는 상태**를 모두 검사해야 합니다.

남는 틈 — 선도 계약 항목도 없는 새 표면 — 은 절차로 닫습니다. `sok ui.expect '{"selector":"…"}'`
가 "no rule" 로 답하면 표면 등록이 먼저입니다.

# L. DOM 내용, 실시간 표면, 주차된 픽셀

네이티브 자식 webview 는 문서 밖에서 합성됩니다. 어떤 DOM `z-index` 도 그 실시간 표면 위로 모달을
올리지 못합니다. 그래서 가시성 트랜잭션은 사실 하나가 아니라 셋을 소유합니다.

1. **내용 가시성.** 활성 workspace·스페이스·탭 사슬이 DOM 슬롯을 마운트된 상태로 보이게 유지합니다.
   오버레이와 레이아웃 움직임은 이를 바꾸지 않습니다.
2. **실시간 표면 가시성.** 문서 밖 표면은 오버레이가 가리는 동안 숨깁니다. 레이아웃 움직임은 compositor
   transaction에서 live 상태를 유지합니다. 비활성 workspace·스페이스·탭 상태는 내용과 표면을 모두 숨깁니다.
3. **픽셀 연속성.** 오버레이가 실시간 표면을 숨기기 전에 그 백엔드가 적용된 픽셀을 캡처합니다.
   `ParkedPicture` 가 그 픽셀을 아직 보이는 DOM 슬롯에 그리고, 실시간 표면이 다시 적용된 뒤에야
   놓습니다. 비활성 사슬은 다른 view가 픽셀을 소유하므로 표면과 그림을 모두 놓습니다.
4. **외곽선 소유.** 카드 frame 이 외곽선의 유일한 소유자이고, 문서가 그것을 그립니다. 관계
   오버레이는 projected seam 만 그릴 수 있고, rail·pane·union 외곽선은 그리지 않습니다.

frame과 focus border는 pointer 입력을 받지 않습니다. resize 입력과 layout 변경은 divider만 소유하고,
border는 commit된 panel rectangle과 같은 위치에 그려집니다. 위치만 바뀌는 React geometry commit은 paint 전에
그 rectangle 위치로 다시 그리고, Core render 없이 발생하는 외부 크기 변경은 `ResizeObserver`가 처리합니다.
두 경로 모두 polling하지 않습니다.

문서 안 터미널은 내용이 계속 살아 있으므로 주차 그림이 필요 없습니다. 문서 밖 브라우저는 모달 아래에서
그림이 보이고 비활성입니다. 두 번째 실시간 렌더러가 아닙니다. 탭 슬롯은 `contentVisible`,
`surfaceVisible`, `visibilityReason` 을 노출하고, 유한 녹화 trace 가 캡처된 프레임마다 display,
visibility, opacity, rect 와 함께 이 값들을 기록합니다.

탭 활성화는 workspace·스페이스·pane·탭의 전체 활성 사슬을 바꿉니다. 영수증은 `changed`와
`layoutMoved`를 분리합니다. 같은 pane 안의 전환은 `changed=true`, `layoutMoved=false`이며 대상 탭
슬롯의 공개 `contentVisible=true` DOM commit을 기다리고 레이아웃 트랜잭션을 열지 않습니다. 기하를
바꾸는 활성화는 트랜잭션을 열기 전에 원인을 선언하고 `layoutMoved=true`를 반환하므로 그 정확한 원인으로
기다릴 수 있습니다. 트랜잭션이 열리지 않으면 대기 중인 원인도 남지 않습니다.

해결된 arrangement는 `railPresent`를 포함합니다. paint 전 준비는 이전 render closure가 아니라 source와
target 해에서 rail 폭을 구합니다. intent host 수명은 workspace identity입니다. render callback 변경은
다음 prepare 호출만 바꾸며 활성 transaction 소유자를 unregister하지 않습니다.

**2026-08-15, 이 빌드에서 실측.** webview 가 불투명했습니다. 이 프레임워크의 `MacBackdropNormal` 이
webview 가 자기 배경을 그리도록 두고, `BackgroundType` 필드는 Linux 와 Windows 에서 읽히고 darwin
에서는 무시되기 때문입니다. 아무도 칠하지 않은 모든 영역이 엔진의 흰색이었습니다 — 모든 테마에서,
모든 workspace 창에서. 투명한 구멍은 브라우저 기능이 아니라 스타일시트 전체가 딛고 선 바닥입니다.

# 판정과 변경

**유지, 이유가 여전히 유효.** R1, R1a, R2, R3, R3a, R4, R5, B1–B8, L. 어느 것도 특정 프레임워크에
의존하지 않습니다. 상자에 대한 명시, 선의 소유자에 대한 명시, 그리고 주장을 숫자로 증명하는 것에 대한
명시입니다.

**변경 — R1a 가 사이드바까지 확장됨.** 행 계약은 처음에 가로로 나란히 선 띠만 다뤘습니다. 세로
이음매를 사이에 두고 마주 보는 사이드바와 콘텐츠 띠에도 같은 규칙을 적용합니다. 이 빌드는 33 과 30
이었습니다. 양쪽 frame은 같은 geometry 계약을 사용합니다.

**변경 — 사이드바의 frame 은 그 플러그인의 것이 아님.** 사이드바 푸터는 플러그인이 푸터 뷰를 선언할
때만 존재했고 높이를 그 플러그인 내용에서 가져왔습니다. 내용에 의존하는 frame 은 frame 이 아닙니다.
플러그인이 없는 빌드에는 사이드바 푸터가 아예 없었고, 그 창의 골격이 다른 모든 창과 달랐습니다. 자리는
테마의 것이고, 플러그인은 거기에 텍스트나 아이콘을 넣을 뿐 높이를 정하지 않습니다.

**해결하지 않고 기록한 모순.** `App.css` 는 chrome 행 높이가 "테마 소유" 라고 명시하고, R4 는 치수
상수가 TypeScript 소스 하나에서 한 번 주입된다고 명시합니다. 둘 다 참일 수는 없습니다. 이 빌드가
따르는 규칙은 R4 입니다. R1 이 테마가 *실제로* 소유하는 padding 손잡이에서 높이를 도출하므로, 테마는
여전히 슬롯을 통해 크기를 정하고, 그 도출이 양쪽을 같게 유지합니다. 어긋난 쪽은 주석이며 그 지점에서
고칩니다.
