# Internationalisation

Every sentence a person reads goes through a key. This document states which sentences those are,
and what the two mechanisms look like.

## I1. Who reads it determines — not what language it is written in

| Reader | Where the sentence is defined |
| --- | --- |
| A person | a key in the bundle |
| A person and an LLM | a key in the bundle |
| An LLM alone | a plain literal |
| A developer alone | a plain English literal |

An English label hardcoded in a handler is exactly as unlocalised as a Korean one. It only looks
correct because the default language is English, and it stays wrong until someone runs the
product in another language and finds a screen half-translated.

Reaching a person includes: rendered text and JSX attributes (`title`, `placeholder`,
`aria-label`, `alt`), command and parameter `description`, command `title`, plugin name and
description, consent text, notification bodies, and any refusal whose text travels back over the
command registry — a `sok` user or a window reads those.

Reaching a person does not include: console output, a wrap that hands a cause to a log
(`fmt.Errorf("reading %s: %w", path, err)`), an invariant a developer reads, a test name, a test
fixture. Those are English literals under 6-1 and gain nothing from a key.

Skill documents (`SKILL.md`) are English. They are authored for an agent and one edition is the
whole surface.

## I2. Two mechanisms, one rule

**The key table** includes short sentences: labels, messages, refusals, `description`. A key
resolves at the moment it is read, in the reader's language.

**Documents** have one English canonical. A reader-facing document may have a matching `.ko.md`
translation. The translation names the English canonical in front matter, follows the same section
order, and defines no independent rule.

## I3. Frontend

`frontend/src/i18n.ko.ts` is the baseline key set and `i18n.en.ts` must hold every key of it —
a missing key fails the compile, so the two cannot drift.

- In a React component: `const t = useT()` then `t("key")`.
- Outside React: `tmsg("key")`.
- Plugin manifest text (`LocalizedText`): `localize(value)`.
- Placeholders are `{name}`: `t("key", { name: value })`.

A key joins an existing namespace. Adding a namespace for one key makes the table a list of
one-offs, and the next author cannot tell where a sentence is owned.

## I3a. A catalogue is registered once and read by everyone

`tmsg` answers in the language of whoever is reading at the moment it is called. The command
catalogue is registered once, at boot, and read afterwards by every caller — a palette, a `sok`
invocation, an agent asking what exists. A description built with `tmsg` at registration is
therefore the sentence for whoever booted the window, and it stays that one for every caller
after. Measured 2026-08-18: `state.tree` answered one identical string to a Korean reader and an
English one, and so did all 448 parameter descriptions.

So a description is **named, not built**. Three shapes carry a sentence, and the shape is what
reports to them apart — nothing guesses whether a string happens to be a key:

| Shape | What it is | Resolved by |
| --- | --- | --- |
| `"…"` | a literal that stands for every language | passes through |
| `key("k")` | a name in this build's table, checked at compile time | `tmsg` |
| `{ en: "…", ko: "…" }` | a plugin's own text, which has no key here | `localize` |

`text(value)` resolves any of the three, and `catalogJson` calls it inside the caller's language
scope. A plugin's map can never be read as a key by accident: a language key is two letters and an
optional subtag, which `i18nKey` is not.

**A plugin declares, the host resolves.** A plugin has no key in this build's table and never
will — it ships on its own schedule and the host never promised it one. Its command description,
its parameter descriptions and the answer its command builds are all `LocalizedText`, handed over
unresolved. A plugin that resolves its own sentence freezes it to the language that call ran in;
for a description that is the language the plugin was registered in, and it never changes again.

**One place determines the language.** `readingLanguage()` answers the reader's inside a scope that
named one, and this window's own otherwise. The key table, `localize`, and the plugin API's
`app.locale()` all read it — so a caller who named a language gets it from all of them, or from
none. Measured 2026-08-18: `app.locale()` read the window's setting alone, and a plugin command
answered an English `sok` call in Korean whenever the window was Korean.

## I4. Go

`core/i18n` holds the mechanism the Go side did not have.

**The language is received, never derived.** Home, socket and identity are handed to this process
by whoever started it, and language is the same kind of fact. Reading a locale here would make
the core answer differently depending on the environment it happens to run in, which is what the
ambient rule refuses (IDENTITY). It arrives on the request envelope, or from the greeting.

**A refusal holds its key, not a finished sentence.** A handler runs before the reader of the
answer is determined: the same refusal goes to a window, to `sok`, and to a log line in one
process. `i18n.Errorf(key, params)` builds it, `i18n.Wrap(cause, key, params)` keeps a cause for
`errors.Is`, and `control.Answer` renders it at the edge, where the caller is in hand. `Error()`
answers English so a log line and a `%v` stay readable.

**A package declares its own sentences** in its `messages.go` through `i18n.Declare`. There is no
shared table to write to, and a key declared twice panics at start rather than answering
whichever line loaded last.

Key names are `<package>.<command or subject>.<what>`.

## I4a. A window answers whoever asked

`control.Answer` renders this process's own refusals at the edge. A window cannot be rendered
there: a delegated command runs in a page with its own display language and no way to see the
request. Measured 2026-08-16, an English `sok` call was answered `TARGET_NOT_FOUND` with its
sentence in Korean.

The transport stamps `callerLanguage` onto the call beside `window`, and overwrites it, so a caller
who sends the name is never believed. **Absent is a fact**: a caller who named no language is not a
caller asking for English, and the window answers in its own.

On the page, **a refusal holds its key**: `notFound("key", params)`. The registry renders it while
the answer is assembled, inside a synchronous scope set to the stamped language — `message`,
`speak` and `hint` are built in one unbroken stretch, so a current-language module value is exact
there. It would not be across an `await`: two callers reading different languages would interleave
and each could finish inside the other's scope. That is the whole reason the refusal is a key.

Gate: `reader_language_gate_test.go` — a refusal rendered before the reader is known is RED.

## I5. Plurals

No `if (n === 1)`. Plural rules differ by language — Korean has one form, English two, Russian
three, Arabic six — so the caller cannot choose one and be right anywhere but where it was written.
The forms are in the table and `Intl.PluralRules` picks one.

```
BAD:   count === 1 ? t("one_item") : t("many_items")
BAD:   "{n} panes"                       ← answers "1 panes"
GOOD:  "{n, plural, one {# pane} other {# panes}}"
```

ICU notation, not a separator: the table already writes prose containing a pipe (`flow | pin`,
`stroke|fill|both`), so a bare separator turns one of those into a form nothing selects.

- `#` is the number. The call site passes `{ n }` or `{ count }` as before.
- A plain sentence stays plain. Most count nothing.
- Korean is written plainly — one category, so a branch is either the only one or dead.
- `=0 {no panes}` wins over the category, which is how a zero case is written without a rule.
- Read with no count, the value is left as written: a caller passing no number is not asking for a
  form, and choosing `other` for them turns every uncounted use into the plural sentence.

Measured 2026-08-16: an English caller asking for one pane was answered "1 panes", and 97 English
sentences counted something with one form. After: "1 workspace in the layout", "3 panes".

## I6. What a test may assert

A test never matches a substring of a sentence another module produces. That makes the sentence
and its assertion two files that must change together, and a translation of one breaks the other
— measured 2026-08-15, 39 assertions across 15 files, one of them matching two characters.

Assert on what a translation does not move: the identifier, the field path, the section number,
or the key itself. Where the source already has a key, resolve it: `toThrow(tmsg("key", params))`
answers in the current language and cannot go stale.

## I7. Gates

| Gate | What it holds |
| --- | --- |
| `korean_gate_test.go` | Hangul stays in bundles or a `.ko.md` translation paired with an English canonical document |
| `catalogLanguage.test.ts` | every catalogue description is a key, counted from what was registered rather than from what two readings have in common; and a plugin's language map resolves against the reader |
| `i18n_gate_test.go` | a shown sentence and a refusal that travels to a caller both come from a key. Refusals outside the rule are listed by sentence with the reason no caller reads them |
| `reader_language_gate_test.go` | a refusal from a window is a key, rendered where the caller is known |
| `plural_gate_test.go` | an English sentence that counts declares both forms; a Korean one declares none |
| `commandMessages.test.ts` | every registered command has a line a person can read |
| `i18n.en.ts` typing | `Record<MsgKey, string>` — a missing English key fails the compile |
| `core/i18n` `Declare` | a key declared twice stops the build |
