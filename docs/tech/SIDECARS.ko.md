# 사이드카

사이드카 소스 manifest, target별 process 필드 생성, 릴리즈 검증은
[RELEASE-INTEGRITY.ko.md](./RELEASE-INTEGRITY.ko.md) 를 따릅니다.

사이드카는 플러그인이 사용하는, 독립적으로 릴리즈되는 프로세스입니다. 코어가 그 프로세스를 시작하고
도메인 payload 를 해석하지 않은 채 control protocol 을 중계합니다. Wails 서비스는 호스트에 컴파일되어
호스트 자체를 확장하므로 사이드카가 아닙니다.

## S1. 식별과 선택

플러그인은 이름이 붙은 사이드카 역할을 선언합니다. 각 역할에는 공개 contract id 와 버전 요구사항이
있습니다. `environment.json` 이 플러그인 역할 하나를 사이드카 ID 하나에 연결합니다. 선택에 폴더 순서,
설치 순서, id 접두사, 대체값을 쓰지 않습니다.

플러그인이 요구사항을 열면 코어가 플러그인 id, 플러그인 버전, 요구사항 이름을 설치 설정 resolver 에
전달합니다. resolver 는 연결된 사이드카를 반환합니다. open 응답에는 실제 사이드카 id 가 담기고, 이후의
send·stream·release 는 그 id 를 사용합니다.

## S2. Manifest

모든 사이드카 artifact 는 soksak-spec-sidecar@0.0.1 을 사용하는 sidecar.json 을 포함합니다. 여기에
사이드카 id 와 버전, 구현한 interface, 설치된 artifact 기준 상대 process 경로를 선언합니다. 이 문서
형식과 검증기는 `soksak-spec` 이 소유합니다.

process 경로는 일반 디렉터리를 거쳐 일반 파일로 해석되어야 합니다. 심볼릭 링크, 경로 탈출, 없는 파일,
선언되지 않은 경로는 거부합니다. 호환용 manifest 는 읽지 않습니다.

현재 호스트는 process 사이드카를 시작합니다. library 를 선언한 manifest 는, 별도로 테스트된 in-process
library 로더를 호스트가 구현하기 전까지 거부합니다.

## S3. 배포

각 사이드카 저장소가 자신의 빌드, 테스트, GitHub Release 를 소유합니다. 릴리즈는 지원 target 마다 불변
아카이브 하나를 게시합니다. 아카이브에는 sidecar.json, dist/<sidecar-id>, 그 프로세스에 필요한 런타임
파일이 들어갑니다. 소스 바이너리는 플랫폼 확장자를 쓸 수 있지만 아카이브 항목은 sidecar.json 이 선언한
경로를 유지합니다.

릴리즈 문서는 target, 아카이브 파일명, 바이트 크기, SHA-256, 형식, 소스 commit, sidecar.json 을
기록합니다. registry 인덱스는 릴리즈 참조 {id, version, size, sha256} 를 기록하고, 모든 위치는 id 와
version 에서 도출합니다. 설치기는 현재 호스트 target 을 선택해 digest 를 검증하고, 트랜잭션 안에서 일반
파일을 풀고, 정확한 버전·target·registry ID·소스 종류·절대 로컬 경로를 `environment.json` 에 기록합니다.
관리 설치는 저장소를 clone 하거나 사이드카를 로컬에서 빌드하지 않습니다.

Local 사이드카 릴리즈는 registry 릴리즈와 같은 manifest, target 아카이브, digest 검증, 설치 트랜잭션을
사용합니다. environment 에는 실체화된 artifact digest 와 `local` 소스를 기록합니다. 자동 registry 갱신이
그 명시적 선택을 대체하지 않습니다.

## S4. 런타임과 프로토콜

사이드카는 application command 를 등록하지 않습니다. 공개 명령은 그 플러그인이 소유합니다. 사이드카
트래픽은 버전이 있는 control envelope 를 사용하며, 코어는 correlation 과 framing 만 검사하고 요청·응답
데이터는 불투명하게 다룹니다. 운영자와 시스템 테스트는 sidecar.request 를 쓸 수 있고, 플러그인 코드는
선언한 app.sidecar 권한을 사용해야 합니다.

준비 완료는 프로세스가 보낸 첫 유효 announcement 입니다. 디스크에 파일이 나타난 것은 준비 완료가
아닙니다. 코어는 유한한 기한으로 announcement 를 기다리며 소켓을 폴링하지 않습니다. 같은 provider 에
대한 동시 open 은 하나의 시작 작업을 공유하고 같은 성공 또는 실패 결과를 받습니다. 다른 시크릿 선언은
기다리기 전에 거부합니다.

## S5. 수명

채널을 놓으면 그 호출자의 연결만 닫히고 사이드카는 멈추지 않습니다. 애플리케이션 종료도 복원 가능한
작업을 소유한 사이드카를 끝내지 않고 연결만 놓습니다. 이후 세대의 애플리케이션은 저장된 프로세스
announcement 를 읽어 다시 연결하고 greeting 을 수행해 같은 프로세스를 사용합니다.
채널 해제는 프로세스를 호스트 상태에서 제거하지 않고 명시적 `sidecar_stop` 을 막지도 않습니다. 그
작업들은 채널 수명이 아니라 프로세스 수명을 다룹니다.

저장된 announcement 는 소유 상태이지 버려도 되는 낡은 데이터가 아닙니다. 이후 세대는 연결과 greeting 으로
상태를 판정합니다. 유효한 소유자는 채택하고, 닿을 수 없는 소유자 기록은 제거하며, 유효하지 않거나 읽을 수
없는 기록은 추측 없이 보고합니다. 정상 종료와 테스트 정리는 공개 수명 작업을 사용하고 테스트 소유 누수가
0인지 확인합니다. 소켓이나 기록을 다른 디렉터리로 옮기는 것은 사고 증거 보존일 뿐이며, 런타임 복구·정리·
개발 소스 수단이 아닙니다.

sidecar.stop 이 사이드카를 끝내는 명시적 작업입니다. 플러그인 비활성화, 뷰 unmount, 앱 재시작은 중지
요청이 아닙니다. 스트림은 자기 id 를 가지며 독립적으로 닫힐 수 있습니다.

열려 있다는 것은 그 주소에서 응답이 온다는 뜻입니다. 보유 중인 유닛의 주소가 연결을 거부하면 그
유닛은 사라진 것입니다. 인벤토리를 읽을 때 잊고, 다음 요청은 처음에 그 유닛을 시작했던 인자로 다시
시작합니다. 호출자는 프로세스 하나가 아니라 이름을 허가받았으므로, 요청은 지금 그 이름을 서비스하는
프로세스에 도달합니다. 이미 종료된 프로세스를 가리키는 run record 는 인벤토리를 읽을 때 잊습니다. 그래서
이름이 기록되어 있는 동안 거부하는 작업은 실행 중인 유닛에만 묶입니다.

응답이 오지 않는 요청은 호출자를 붙들지 않고 종료합니다. 요청을 받고 아무것도 보고하지 않는 유닛 —
살아 있지만 서비스할 수 없는 프로세스, 쓸 공간이 없는 디스크 — 은 그렇지 않으면 요청한 플러그인, 그
플러그인 뒤의 큐, 그리고 입력하는 사람까지 붙듭니다. 대기에는 상한이 있고 거부 메시지는 유닛 이름과
그 상한을 담습니다.

## S6. 시크릿과 권한

플러그인 manifest 가 사이드카 권한과 이름이 붙은 요구사항을 공개합니다. 시크릿 값은 JavaScript 로
넘어가지 않습니다. 플러그인은 시크릿 이름이나 생성 시크릿 선언을 전달하고, 코어가 프로세스 경계에서 값을
해석합니다. 실행 중인 사이드카를 다른 시크릿 선언으로 다시 여는 것은 거부합니다.

## S7. 테스트

- 각 사이드카 저장소가 sidecar.json 을 검증하고 선언된 process 를 stage 하며 자기 프로토콜과 적합성을
  테스트합니다.
- `soksak-spec` 이 사이드카 manifest 형식을 테스트하고 게시합니다.
- 코어는 environment 결합 해석, 경로 안전성, 프로세스 수명, 채택, 불투명 중계를 테스트합니다.
- min-median-max/soksak-terminal-tests 는 설치된 다중 provider 동작을 테스트하며 소유자 소스 트리를
  빌드하지 않습니다.
