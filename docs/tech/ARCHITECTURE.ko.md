# 구조

코어는 구체적인 내용을 그리지 않습니다. 터미널, 브라우저, 사이드바 본문은 플러그인으로 들어오고,
코어는 프레임과 registry, 그리고 그 전부를 관측 가능하게 만드는 표면을 소유합니다.

## 코어가 소유하는 것

| 인터페이스 | 보장 |
| --- | --- |
| 레이아웃 | 재귀 `leaf \| split` 트리 하나. 분할, 이동, 닫기, 최대화, 크기 조절. 트리는 플러그인에게 불투명합니다. 명령으로만 바뀌며 넘겨주지 않습니다. |
| 명령 registry | registry 하나. 코어·프레임워크·플러그인의 모든 명령이 타입 있는 매개변수 schema 와 함께 한 번 등록합니다. 거기 없는 명령은 존재하지 않습니다. |
| view·program registry | `registerView(viewId, provider)` 와 `contributes.programs[]`. mount 와 unmount 는 수명만 소유합니다. 추가 메뉴는 program registry 의 반영본입니다. |
| 테마 | 토큰 슬롯과 chrome 속성. 컴포넌트는 값이 아니라 슬롯을 소비하므로, 새 테마는 모든 규칙을 고치는 일이 아니라 문서 하나입니다. |
| 주소 | 조작 가능한 모든 노드의 구조 경로. 선택자를 추측해서 닿는 것은 없습니다. |
| 캡처 | 포커스 없이, 가려진 상태에서도 읽는 창의 픽셀. |
| 저장, 스캔, identity, 활동, HTTP | 호스트와 무관한 답이며 창이 없어도 닿습니다. |

네이티브 능력은 코어에 남습니다. PTY 의 커널 객체와 플랫폼 webview 는 플러그인 구분을 넘을 수 없기
때문입니다. 코어는 그것을 일반 능력으로 노출하고 플러그인은 얇은 클라이언트로 소비합니다.

그것이 C6 의 세 번째 질문이며, 셋 중 가장 좁은 조건이지 열린 문이 아닙니다. 코어는 PTY 를 소유합니다.
어떤 shell 의 프롬프트 프로토콜도, shell 경로 목록도, shell 이 낸 바이트가 무슨 뜻인지에 대한 규칙도
소유하지 않습니다. 플러그인이 *가질 수 있는* 것은 플러그인이 가집니다.

## 네 이음매

플러그인은 정확히 이 넷으로만 붙습니다. 비공개 채널도, 저장소 직접 import 도, 네이티브 명령으로 가는
뒷문도 없습니다.

1. **program** — `contributes.programs[]` 가 진입점을 선언하고 코어가 그리로 라우팅합니다.
2. **view** — `contributes.views[]` 와 `registerView`. 제공자는 view context 만 받습니다. 다른 view 의
   DOM 을 읽거나 포커스하는 것은 금지합니다.
3. **명령** — 타입 있는 schema 로 한 번 등록하면 CLI 와 control plane 에서 자동으로 닿습니다.
4. **능력** — 권한 검사를 지나는 `app.*` 와 이벤트 버스.

이 넷으로 표현할 수 없는 것이 플러그인이 해서는 안 되는 것입니다. **실제 플러그인을 이 안에서 만들 수
없다면 코어에 일반 능력이 빠진 것입니다** — 그 능력을 추가합니다. 비공개 경로는 절대 추가하지
않습니다.

## 원칙

전부 강제 규칙입니다.

- **A1.** 코어는 구체적인 내용을 그리지 않습니다. 슬롯은 빈 컨테이너입니다. 창에는 region 셋
  — `left`, `center`, `right` — 이 있고, 플러그인은 자기 view 가 어느 region 에 놓이는지 하나 또는
  여럿을 선언합니다. region 은 위치이지 역할이 아닙니다. 코어에는 view 가 무엇을 위한 것인지에 대한
  개념이 없습니다.
- **A2.** view context 가 view 로 들어가는 유일한 채널입니다. 코어 저장소도, 레이아웃 트리도
  없습니다.
- **A2a.** 섹션 하나가 플러그인 하나입니다. 파일 트리, 데몬 목록, 북마크, 터미널 각각이 자기가 놓일
  region 을 선언하는 별개 플러그인이며, 어떤 플러그인도 다른 플러그인의 섹션을 제공하지 않습니다.

  **무엇이 무엇과 함께 나타나는지는 별개 질문이고, 그 답은 workspace 가 가집니다.** manifest 는
  region 을 선언할 뿐 동반자를 선언하지 않습니다. 어떤 섹션이 어느 region 에 열려 있는지, 분할인지
  탭인지, 순서가 무엇인지는 workspace 의 상태입니다. 사람이 배치하고, workspace 와 함께 저장되고,
  함께 복원됩니다(`leftLayout`, 오른쪽도 같습니다). 플러그인은 자기가 무엇 옆에 나타나는지 말할 수
  없고, 코어도 그것을 정하지 않습니다.
- **A3.** 일반 능력만 만듭니다. 소비자 하나의 이름을 딴 능력은 종속입니다.
- **A4.** 코어 종속 금지. 내용 하위 시스템을 추가해도 코어 변경은 0입니다.
- **A5.** schema 가 단일 진실입니다. 산문은 schema 가 강제할 수 없는 것만 더합니다.
- **A6.** 멱등. 활성화, mount, 명령은 몇 번을 실행하든 같은 상태로 수렴합니다.
- **A7.** 독립. 각 플러그인은 자기 빌드와 테스트를 가진 자기 저장소이며, 선언한 의존 밖의 어떤 것에도
  기대지 않습니다.
- **A8.** 제거 가능. 어떤 플러그인을 꺼도 코어와 무관한 플러그인은 그대로 동작하고, 남는 네이티브
  자원도 없습니다.
- **A9.** 코어 변경 0. 코어를 고치게 만드는 플러그인은 빠진 능력입니다.

## 결합 법칙

- **C1.** 코어에는 특정 플러그인도, 특정 기능도 없습니다.
  검사: `coupling_gate_test.go` 가 `frameworks/` 를 포함한 코어 소스에서 플러그인 id, 렌더링 엔진,
  그리고 **도메인 개념**을 훑습니다. 이름과 개념은 서로 다른 두 읽기입니다. 플러그인 id 를 하나도
  적지 않았지만 `Bookmark { url, title }` 을 보유한 코어는 브라우저에 똑같이 강하게 결합돼 있기
  때문입니다. 2026-08-16 실측: id 검사는 하루 동안 GREEN 이었고, 그동안 코어는 북마크 저장소,
  `bookmark.*` 명령 셋, `bookmarks.changed` 플러그인 이벤트, 브라우저 패널의 스타일시트를 보유하고
  있었습니다.
- **C1a.** 코어는 설치본이 선언한 것에서 조립하며, 자기 소스에서 조립하지 않습니다. 어떤 플러그인
  패키지도 코어 바이너리에 링크되지 않습니다.

  플러그인은 설치되는 것입니다. 코어가 조립하려고 읽는 것은 manifest 와 그 옆의 산출물이지 import 가
  아닙니다. 이름이 코어 소스에 있는 플러그인은 설치된 것이 아니라 컴파일된 것입니다. 그것을 지우면
  빌드가 깨지고, 다음 것을 더하려면 코어를 고쳐야 하며, 둘 다에 대해 A9 가 거짓이 됩니다.

  설치 선언은 해석된 조립 그래프(COMPOSITION.md)이지 디렉터리의 존재가 아닙니다. 코어의 테스트와
  task 는 형제 플러그인·사이드카 저장소를 훑지 않습니다.

  프로세스 안에서 도는 것과 링크된 것은 다르며, 그것을 같게 읽은 탓에 둘이 코어에 들어왔습니다.
  이 프로세스에서 실행되어야 하는 네이티브 반쪽 — 부모 view 는 프로세스 지역이고, 메시지 펌프는 이
  프로세스의 주 큐가 필요합니다 — 은 **엔진 모듈**입니다. 설치본이 선언했기 때문에 코어가 적재하는
  dylib 이며, 자기가 export 하는 심볼로 기술되고, 코어는 그 메시지를 이해하지 않고
  중계합니다(`SIDECARS.md` S3).

  검사: `coupling_gate_test.go` 가 `go list -deps` 를 읽어 코어 바이너리의 의존 그래프에 있는 플러그인
  패키지를 거부합니다. 네이티브 반쪽 둘이 이미 그들을 위해 존재하는 이음매 뒤로 옮겨질 때까지 이
  검사는 RED 입니다.

- **C1b.** 플러그인이 어떤 형태를 가질지는 하는 일에서 읽어내는 것이지 고르는 것이 아닙니다.

  플러그인의 표면은 문서 안의 view 입니다. 그 밖에 필요한 것은 아래에서 일을 해낼 수 있는 첫 형태를
  씁니다.

  | 하는 일 | 형태 |
  | --- | --- |
  | 문서 안에만 그린다 | view 하나 |
  | 자기 수명을 가진 일, 또는 이 프로세스가 지지 않아야 할 일 | control plane envelope 를 쓰는 자기 프로세스 |
  | pane 의 표면에 그린다 | 코어가 적재하는 엔진 모듈(`SIDECARS.md` S3) |

  모든 분기가 사실 판단입니다 — 그리는가, 창보다 오래 살아야 하는가, view 가 프로세스를 떠날 수
  있는가 — 그래서 두 독자가 같은 형태에 도달합니다.

  세 번째 분기는 선호가 아닙니다. view 는 프로세스 구분을 넘지 못합니다. 2026-08-20 실측으로 macOS
  에는 공개 API 가 없고, Windows 에서는 DPI 인식이 초기화되며, 이 프레임워크가 기본으로 빌드하는
  GTK4 에는 아무것도 없습니다. 자기 프로세스로 배포된 그리기 플러그인은 세 target 중 하나에서만
  동작합니다.

- **C1c.** 코어는 플랫폼이 그것을 제공하고 코어가 이미 그것에 의존할 때만 내용 종류를 소유합니다.

  창 자신의 webview 가 그런 종류입니다. 코어가 그 위에 세워졌고 그것은 하나뿐입니다. pane 이 그리는
  그 밖의 것은 엔진 모듈로 들어옵니다.

  **판정: 같은 것의 두 번째 구현을 코어 변경 없이 설치할 수 있는가.** 답이 아니오인 곳에서 코어는
  능력이 아니라 내용 종류를 보유한 것이고, 그것은 밖으로 나갑니다. 이 판정은 의견이 아닙니다. 어느
  날인지 말하며 그날은 가정이 아닙니다. 이것이 잇는 이전 구현은 브라우저 셋을 배포했고, 하나는
  플랫폼 webview 위에, 둘은 자기 엔진 위에 있었습니다.

- **C2.** 모든 기능은 명령·status·DOM 세 표면을 노출하며, 그 노출은 장식이 아니라 조작 가능해야
  합니다. 명령이 없는 view 는 실패입니다. 어떤 status 축도 볼 수 없는 view 는 실패입니다. 선택자를
  추측해야만 닿는 요소는 배포하지 않습니다.
  **조작 가능**이란 노출된 노드를 밖에서 구동한다는 뜻입니다. `ui.input.click`, `ui.input.drag`,
  `ui.input.dnd`, `ui.input.key`, `ui.input.fill` 이 `ui.tree` 가 답한 주소에 작용하고,
  `ui.input.observe` 가 무엇이 도착했는지 보고합니다. 읽기만 되는 주소는 그림이고, 그림은 이음매가
  아닙니다. 같은 트리를 답하면서 다르게 동작하는 두 빌드는 그것으로 구별되지 않기 때문입니다.
- **C2a.** 한 창에서 노출된 DOM 주소는 모두 고유합니다. 반복되는 영역은 pane 축을 주소에 추가하며,
  분할로 인해 두 요소가 같은 영역 전용 경로를 답해서는 안 됩니다. 따라서 노출 표면을 승인하기 전에
  `ui.tree.duplicates` 는 비어 있어야 합니다.
- **C3.** 플러그인은 선언을 통해서만 다른 플러그인의 구분을 넘습니다. 다른 플러그인의 DOM, 내부 상태,
  파일 배치, 적재 순서를 읽지 않습니다.

  의존 형태는 둘이며 서로 다른 요구를 표현합니다.

  - 구현 의존은 플러그인·사이드카·kit 의 id 와 버전을 이름 짓습니다. 그 구현이 필요할 때 씁니다.
    사용자에게 보이는 활성화 뿌리는 플러그인뿐입니다.
  - `consumes` 는 정확한 공개 계약 버전 하나를 이름 짓습니다. 제공자는 `implements` 에 같은 정확한
    계약 버전을 선언합니다. 그 계약의 어떤 구현이든 유효할 때 씁니다.

  둘 다 선택입니다. 독립 플러그인은 어느 쪽도 선언하지 않습니다. 계약은 구현이나 소비자 여럿이 같은
  공개 동작을 요구한 뒤에만 도입합니다.
- **C3a.** 공유 계약은 공통 동작만 다룹니다. 구현마다 다른 설정·명령·status 는 그 플러그인 자신의
  명세에 남습니다.

  계약 선언 자체는 권한이 아닙니다. 명령·프로세스·데이터의 일반 권한 검사는 그대로 적용됩니다.
  플러그인 사이의 호출 지점에서는 정확한 플러그인 의존이거나, 소비·제공 계약이 호환되어야 합니다.
  선언이 없거나, 형식이 틀렸거나, 호환되지 않으면 거부합니다.

- **C4.** 코어에는 spec 하나가 있고 플러그인에는 자기 것이 있습니다. `CORE_SPEC` 은 코어가 정의하는
  envelope 에 찍는 버전입니다. 플러그인 런타임 전송이며 그 양끝이 모두 코어의 것입니다. 플러그인의
  manifest 가 그 플러그인의 spec 이고, 플러그인 id 가 그것을 이름 짓습니다. 공유 도메인 계약은 코어
  밖의 별도 버전 문서입니다. 제공자와 소비자가 그것을 참조하며, 코어는 도메인 필드를 해석하지 않고
  id 와 버전만 비교합니다.

  코어가 읽지만 발행하지 않는 문서는 그 발행자가 도장을 찍고 코어는 그 도장을 읽습니다. registry
  인덱스, 릴리즈 manifest, 적합성 보고서, 그리고 plugin·sidecar·kit manifest 가 그렇습니다. 각 문서
  형식에는 선언된 버전이 하나 있습니다.

  형식은 문서 종류마다 하나입니다. `soksak-spec-plugin@` 은 모든 플러그인이 공유하는 manifest
  형식입니다. 플러그인마다 형식을 두면 플러그인 id 가 이미 담고 있는 identity 를 중복하게
  됩니다(C1).

- **C5.** 표준은 조용히 약해지지 않습니다. 옳은 표준에 대한 RED 는 구현, fixture, 노출된 인터페이스를
  고치라는 뜻입니다. 표준 자체가 틀렸다면 증거와 테스트를 같은 commit 에 담아 공개적으로 바꿉니다.

- **C6.** 공통은 코어로 가고 기능은 절대 가지 않습니다. **기능이란 내용이 무슨 뜻인지 또는 어떻게
  동작해야 하는지에 대한 판단을 담은 코드입니다.** 그것이 판정의 전부이며, 아래 세 질문이 그것을
  적용하는 방법입니다.

  둘은 필요조건입니다. 하나라도 어기면 플러그인의 것입니다.

  1. **어떤 도메인의 이름도 따지 않았다.** `app.data`, `app.process`, `ui.input` 은 기제를 이름
     짓습니다. `bookmark`, `favicon`, `tabstrip` 은 내용 종류 하나를 이름 짓고, 그 이름만으로 이
     코드가 어느 플러그인을 위해 쓰였는지 드러납니다.
  2. **첫 소비자를 한 번도 본 적 없는 플러그인이 고치지 않고 쓸 수 있다.** 이름공간을 키로 하는
     저장소는 브라우저와 메일 클라이언트를 똑같이 지원합니다. `{ url, title }` 을 보유한 저장소는 둘
     중 하나만 지원합니다.

  그다음 아래 중 하나가 애초에 코어에 있는 이유입니다.

  3. **플러그인 구분을 넘을 수 없거나** — 플랫폼 webview, 창의 픽셀. 창을 소유한 프로세스가 그것을
     소유합니다 — **아니면 모든 플러그인이 그것을 각자 다시 만들게 되거나**, 그것도 서로 다르게
     만들게 됩니다. OSC 7/133/633 의 바이트 스트림 파서는 구분을 잘 넘지만 여전히 코어의 것입니다.
     그것은 프로토콜을 해독할 뿐 아무것도 판단하지 않으며, 터미널 바이트 스트림을 읽는 플러그인 셋은
     각자 그것을 다시 쓰게 됩니다.

     PTY 는 공유 **능력**이며, 터미널 의미를 코어에 넣을 이유가 되지 않습니다. 그 능력의 구현은
     선언되고 설치됩니다. `soksak-spec-pty` 에 대한 `soksak-sidecars/soksak-sidecar-pty` 입니다.
     그러면 두 번째 구현 — 다른 플랫폼의 콘솔 API, 다른 머신의 shell — 이 코어 변경 없이 설치되며,
     그것이 C1c 가 적용하는 판정이고, 코어는 내용 종류 하나를 위한 장치 계층을 보유하지 않습니다.

  둘을 가르는 것은 판단입니다. OSC 133 파싱은 해독입니다. "출력이 800ms 끊기면 turn 이 끝난 것이다"
  는 판단입니다. "저장한 페이지는 url 과 title 이다" 는 판단입니다. "파일 탭에는 코드 모드와 미리보기
  모드가 있다" 는 판단입니다. 판단은 플러그인이 존재하는 이유입니다.

  이 규칙이 막는 실패는 편안한 쪽입니다. 기능이 코어로 오는 이유는 코어가 쓰기 가장 쉬운 곳이기
  때문입니다. 저장소 하나, 명령 표 하나, 스타일시트 하나가 이미 거기 있습니다. 그리고 그 결과에는
  잘못돼 보이는 구석이 없습니다. 그다음 같은 종류의 두 번째 플러그인이 그중 어느 것도 쓸 수 없습니다.
  전부 첫 번째를 위해 만들어졌기 때문입니다.

## 백엔드 하나, 전송 여럿

명령은 한 번 등록하고 모든 전송으로 닿습니다. 프론트엔드의 `invoke` 와 socket 호출이 같은 표에서
해석되며, 어떤 것도 그것을 우회할 수 없습니다. 두 번째 경로는 첫 번째에서 어긋나고, 그 어긋남은 둘이
다른 답을 낼 때까지 드러나지 않습니다.

registry 항목은 소유자를 선언합니다. `core` 는 창에서도, 헤드리스 서버에서도, 테스트에서도 같은 답을
합니다. `framework` 는 이 호스트의 창이 필요합니다. 창이 없는 프로세스에는 설정할 배경도, 다시 보낼
대기 envelope 도 없습니다.

표는 자기 자신에 대해서도 답합니다. 무엇을 서비스하는지와 함께 무엇을 거부하며 왜 거부하는지를
보고합니다. "알 수 없는 명령" 만 받은 호출자는 "아직 안 만들었다" 와 "여기서는 불가능하다" 를 구분할
수 없고, 그러면 이미 끝난 조사를 다시 하거나 그 명령을 직접 구현하게 됩니다.

## Identity

프로세스는 자기 식별자를 받고 나머지 전부를 거기서 한 번에 도출합니다. home 과 식별자를 따로
도출하면 "A 의 home 에 B 의 이름" 이라는 짝이 표현 가능해지고, 재연결이 잘못된 설치본에 닿습니다.

home 은 환경 축으로만 나뉩니다 — `~/.soksak-<env>`. 프레임워크 축으로는 의도적으로 나누지 않습니다.
home 하나가 백엔드 하나를 담고 프론트엔드는 여럿일 수 있습니다.

코어의 어떤 것도 프로세스 환경을 읽지 않습니다. launcher 가 한 번 읽어 값을 내려보내므로, 규칙이 누가
불렀는지에 따라 다르게 답할 수 없습니다.
