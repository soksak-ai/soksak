# 플러그인 데이터 암호화 — at-rest 필드 봉인

플러그인이 `app.data` 에 저장하는 민감값(메모 속 비밀번호·토큰 등)을 **DB 파일이 새어나가도 평문으로 안 보이게** 하는 최소 안전. 필드 단위. 이 문서는 플러그인 저자와 운영자용이다. 기본 사용법은 `docs/DB-메뉴얼.md`, 여기선 암호화만 다룬다.

## 0. 무엇을 막고, 무엇을 안 막나

**막는다(위협)** — DB/데이터가 **보호 맥락 밖으로 새는** 경우 평문 금지:
- 클라우드 백업/동기화(iCloud·Dropbox·Time Machine)로 `~/.soksak` 이 나감
- 버그 리포트·로그 번들에 `.db` 가 첨부됨
- 멀티유저 기계에서 다른 사용자가 파일을 읽음
- 비암호화 디스크 노트북 도난

**안 막는다(OS·디스크 암호화 몫)** — 이걸 재현하는 건 과잉이다:
- 로그인된 기계 앞의 공격자, **동일-사용자 악성코드**(그 사용자로 도는 코드는 어차피 SSH 키·쿠키 다 읽는다)
- OS/세션 자체가 뚫린 상황

즉 "내 컴퓨터 데이터의 최소 안전"이지 풀 디스크 보안이 아니다.

## 1. 컬럼(필드)에 암호화가 필요할 때 — 어떻게

봉인 여부는 **`define` 이 정한다**(별도 `encrypt:true` 플래그 없음):

- `indexes`/`fts` 로 선언한 필드 = **평문**(질의·정렬·검색되게 — 그래서 노출).
- `id`(내장) = **평문**(레코드 키).
- 선언 안 한 나머지 doc 필드 = **봉인**(암호문) — 그 scope 에 암호화가 켜져 있을 때.

```js
await app.data.define("notes", {
  indexes: ["folderId", "createdAt"],   // 평문 — 비민감만
  fts:     ["title"],                    // 평문 — 비민감만
});
await app.data.put("notes", {
  folderId: "f1", title: "배포 노트",     // 평문(질의/검색)
  token: "ghp_xxx", body: "…민감…",       // 봉인(암호문 at-rest)
}, { scope });
```

**규칙**
- 암호화가 필요한 필드는 **`indexes`/`fts` 에 넣지 마라** → 자동 봉인.
- **민감값을 `indexes`/`fts` 로 선언하면 평문이 된다(금지).** 검색이 필요하면 비민감 필드만 대상으로.
- 봉인 필드는 **질의·정렬·검색 불가**(암호문이라). 비민감 인덱스로 좁혀 doc 을 받아 앱에서 처리한다.
- **투명**: 봉인·복호는 코어가 자동. 플러그인 `put`/`get` 코드는 바뀌지 않는다.

## 2. 키는 코어가 OS 에 맡긴다 (플러그인 무관)

- 데이터 키는 **OS 시크릿 저장소**에 있다: macOS **Keychain**, Windows **DPAPI**, Linux **libsecret**. 앱이 시작 시 투명하게 취득한다(일상 passphrase 없음).
- **키는 파일이 아니라 DB/폴더 유출에 안 따라간다** — 그래서 DB 가 새도 봉인 필드는 암호문으로 남는다.
- keyId/버전은 각 레코드에 태그되고(envelope), 로테이션 시 옛 키로 복호→새 키로 재봉인한다 — 자동. 플러그인은 키·keyId 를 만지지 않는다.

## 3. 복구코드 (이식·복원)

키가 기계 바인딩이므로, **다른 기계/OS 로 옮기거나 키체인을 잃으면** 봉인 데이터를 복호할 수단이 필요하다.

- 암호화를 처음 켤 때 코어가 **복구코드를 1회 표시**한다(사용자가 저장, 앱은 저장 안 함).
- 백업에는 데이터 키를 이 복구코드로 감싼 blob 이 함께 들어간다 — 코드 없이는 무의미(고엔트로피).
- 새 기계/복원: 사용자가 복구코드를 입력 → 키를 풀어 그 기계 OS 저장소에 심는다 → 봉인 데이터가 열린다.
- **정직한 대가**: 기계도 잃고 복구코드도 잃으면 복구 불가(암호화 본질 — 백도어 없음). 복구코드가 안전망이다.

## 4. 키 변경

- **키 로테이션**: 새 데이터 키로 전 봉인 필드를 재봉인(중단 시 재개 가능), OS 저장소·복구 blob 갱신. 주기적·의심 시.
- **복구코드 변경**: 데이터 키를 새 복구코드로 다시 감싼다(데이터 재암호화 없음). 코드 분실/노출 시.

## 5. 크로스플랫폼·한계

- 세 OS 동작 동일. 크립토는 순수 Rust(XChaCha20-Poly1305 + AAD), OS 는 **키 저장만** 위임.
- **보호 세기 차이(정직)**: macOS Keychain 은 앱 코드-신원 ACL 이라 다른 프로그램이 키를 못 꺼낸다(per-app, 최강). Windows DPAPI·Linux libsecret 은 per-user 라 **같은 사용자로 도는 악성코드는 키를 꺼낼 수 있다** — 이는 OS 의 한계이자 우리 스코프 밖(§0).
- **no-secret-service**(예: OS 시크릿 저장소 없는 헤드리스 Linux): 봉인이 **불가 상태**로 노출되며, 평문을 봉인인 척 저장하지 않는다(무음 폴백 금지).

## 6. 확인

- `secret.status`(CLI/MCP/AI) 로 봉인 가용 여부·백엔드(keychain/dpapi/libsecret/none)·활성 keyId·복구 가용을 조회한다.
- 봉인이 실제로 되는지 검증: `.db` 를 외부 sqlite 로 열어 그 필드 값이 **암호문**(평문 아님)인지 확인.
